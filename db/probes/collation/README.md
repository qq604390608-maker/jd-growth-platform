## 2. 原始输出（原样转录）

### 2.1 `/order` · ORDER BY 各种写法

原样 SQL 形态：`SELECT item_name FROM probe_collation ORDER BY item_name [COLLATE ...]`

| 写法 | 原样返回顺序（数组即返回序） |
| ---- | ---- |
| **默认 `ORDER BY item_name`** | `APP / 小程序 / PC` → `CDP 用户标签系统` → `HVA 研究 · 追问` → `glm-5.3 备选` → `候选行为获得支持（仍属候选）` → `已停止` → `智能体` → `运行中` → `首页推荐位 / 搜索结果页` → `黄金眼` |
| `ORDER BY item_name DESC` | `黄金眼` → `首页推荐位 / 搜索结果页` → `运行中` → `智能体` → `已停止` → `候选行为获得支持（仍属候选）` → `glm-5.3 备选` → `HVA 研究 · 追问` → `CDP 用户标签系统` → `APP / 小程序 / PC` |
| `COLLATE BINARY` | **与默认完全相同** |
| `COLLATE NOCASE` | `APP / 小程序 / PC` → `CDP 用户标签系统` → **`glm-5.3 备选`** → **`HVA 研究 · 追问`** → `候选行为获得支持（仍属候选）` → `已停止` → `智能体` → `运行中` → `首页推荐位 / 搜索结果页` → `黄金眼` |
| **`ORDER BY order_no`（对照）** | `运行中` → `已停止` → `智能体` → `黄金眼` → `CDP 用户标签系统` → `HVA 研究 · 追问` → `glm-5.3 备选` → `候选行为获得支持（仍属候选）` → `APP / 小程序 / PC` → `首页推荐位 / 搜索结果页` |

**原样结论：**
- 默认序 = **字节序**：ASCII 开头段（`APP` < `CDP` < `HVA` < `glm`）在前，中文段按 UTF-8 字节升序（候 `E58099` < 已 `E5B7B2` < 智 `E699BA` < 运 `E8BF90` < 首 `E9A696` < 黄 `E9BB84`）。**不是拼音序**。
- `COLLATE NOCASE` **确实改变了顺序**：`glm-5.3 备选` 与 `HVA 研究 · 追问` 的相对次序与默认序**相反**——因为 NOCASE 折 ASCII 大小写后 `g` < `h`。**但中文段的相对次序完全不变**（候/已/智/运/首/黄），即 NOCASE 对中文无效。
- `order_no` 给出的序与前四行**全都不同**，说明展示序无法从 `item_name` 的任一种排序规则推导出来。

### 2.2 `/like` · LIKE 行为

| 表达式 | 原样命中 |
| ---- | ---- |
| `LIKE '%中%'` | `运行中` |
| `LIKE '%研究%'` | `HVA 研究 · 追问` |
| `LIKE '%cdp%'`（小写） | `CDP 用户标签系统` ✅ 命中 |
| `LIKE '%CDP%'`（原样大写） | `CDP 用户标签系统` |
| `LIKE '运_中'`（`_` 单字符通配） | `运行中` |
| `LIKE '%/%'`（斜杠） | `APP / 小程序 / PC`、`首页推荐位 / 搜索结果页` |
| `LIKE '%（%'`（中文左括号） | `候选行为获得支持（仍属候选）` |
| `LIKE '运行中'`（精确） | `运行中` |
| `LIKE '运行中 '`（多一个尾空格） | **空** |

**原样结论：** `LIKE` 对中文可做**子串**匹配，`_` 单字符通配对中文有效；**对 ASCII 大小写不敏感**（`%cdp%` 命中 `CDP`）；**尾空格是有效字符**（多一个空格即不命中）。

### 2.3 `/glob` · GLOB 行为

| 表达式 | 原样命中 |
| ---- | ---- |
| `GLOB '*中*'` | `运行中` |
| `GLOB '*cdp*'`（小写） | **空** |
| `GLOB '*CDP*'`（原样大写） | `CDP 用户标签系统` |
| `GLOB '运?中'`（`?` 单字符通配） | `运行中` |
| `GLOB '*/*'`（斜杠） | `APP / 小程序 / PC`、`首页推荐位 / 搜索结果页` |
| `GLOB '*（*'`（中文左括号） | `候选行为获得支持（仍属候选）` |

**原样结论：** `GLOB` 对中文可匹配，`?` 单字符通配对中文有效；**区分大小写**（`*cdp*` 不命中 `CDP …`）——与 `LIKE` 相反。

### 2.4 `/in` · IN 行为

| 表达式 | 原样命中 |
| ---- | ---- |
| `IN ('运行中','黄金眼','不存在')` | `运行中`、`黄金眼` |
| `IN ('运行中 ')`（尾空格） | **空** |
| `IN ('cdp 用户标签系统')`（小写） | **空** |
| `IN ('CDP 用户标签系统')`（原样） | `CDP 用户标签系统` |
| `IN ('已停止','智能体','HVA 研究 · 追问')` | `已停止`、`智能体`、`HVA 研究 · 追问` |

**原样结论：** `IN` 是**按字节精确匹配**：**区分 ASCII 大小写**（与 `LIKE` 相反）、**尾空格敏感**。

### 2.6 独立参考序（第三方计算，与本探针无关）

| 参考 | 结果 |
| ---- | ---- |

## 3. 结论：前端下拉顺序是否必须依赖数据库排序？

### 3.1 直接回答

**不能依赖数据库对"中文名"的默认排序**——D1 给的是字节序（= 码点序），不是拼音序，也不报错（🔴 静默给错序）。

**但枚举下拉必须有确定的顺序**，顺序来源只有两种：

| 方案 | 顺序来源 | 是否依赖 DB 排序 | 结论 |
| ---- | ---- | ---- | ---- |
| **A · 用字典表已有的 `order_no`** | 数据（种子/维护端填写） | ❌ 不依赖 | **推荐**：顺序由业务决定，与排序规则、ICU 版本无关 |
| B · 应用层按拼音排序 | 运行环境 `Intl.Collator` | ❌ 不依赖（但依赖 ICU） | 仅在"必须按拼音"时用，见 §3.2 工作量 |

**所以答案是：前端下拉顺序不必依赖数据库排序；应由 `CFG-08 dict_item.order_no` 决定。**

### 3.2 若选 B（应用层排序），工作量在哪

1. **每个取数点都要加排序**：F-27 目标列表、F-28 机会列表、各字典下拉、来源/触点清单……凡按中文展示的列表都要各写一遍 `Intl.Collator('zh-Hans-CN')`。
2. **与分页冲突**（最大工作量）：DB 层无法按拼音排序，因此**不能在 DB 分页**——必须"全量取出 → 应用层排序 → 再分页"，或放弃 DB 分页。这是结构性改动，不是加一行排序。
3. **结果随环境漂移**：拼音序依赖 ICU 版本（本机 ICU 78.3）。不同 Node / 浏览器 / 部署环境的 ICU 版本差异会让同一份数据排出不同顺序，且**不报错**。
4. **仍表达不了业务顺序**：拼音序只是"字典序"，无法表达状态生命周期序等业务期望（如 `running → blocked → stopped → done`）。最终仍需回到 `order_no` 一类显式字段。

### 3.3 影响面

- **字典/枚举类**（CFG-07/08）：走 `order_no`，**不受影响**。
- **非字典的中文列表**（F-27 目标列表、F-28 机会列表、来源/触点清单）：`order_no` 不适用，仍属 `tech-stack.md` §3.2 的 ① 应用层排序 / ② 增设排序键列二选一，**本轮未裁决**（TS-12 剩余部分）。

## 4. 顺带确认：字典表加 `sort_order` 列能否彻底规避？

### 4.1 结论：能，且该列**已存在**

`CFG-08 dict_item` 已有 **`order_no` `int` `NOT NULL`，口径「展示顺序」**（`schema.md:621`）。

因此**不需要新增列**——"加 sort_order 列"这个动作在 `schema.md` 里已经完成（只是叫 `order_no`）。

### 4.2 最小改动方案（**不实施，仅列出**）

零 schema 改动，只需三条约定：

1. **查询侧**：凡字典下拉/列表，一律 `ORDER BY order_no`；**禁止** `ORDER BY item_name`（后者会静默给字节序）。
2. **种子侧**：为每个 `dict_item` 填 `order_no`。`NOT NULL` 已保证非空，但**未保证同一 `dict_type_code` 内不重号**——重号时排序不确定。
3. **维护侧**：新增/调整字典项必须给 `order_no`。

### 4.3 可选增强（**需 PM/技术方裁决，本文件不选**）

- 是否加 `UNIQUE(dict_type_code, order_no)` 以杜绝同类型重号——需与「停用不删除」（`is_active`）策略一起评估，属取舍，**本文件不裁决**。
- 是否需要对 `item_name` 也保留一个拼音排序键（供"按拼音"场景）——属 TS-12 的非字典列表部分，**本轮未覆盖**。

## 6. 可直接粘进 `tech-stack.md` 的结论句

> **TS-12（实测）**：D1 默认 `ORDER BY` 对中文是 **BINARY 字节序（= Unicode 码点序）**，不是拼音序，也不报错——10 条真实字典口径的默认序为 `APP / 小程序 / PC → CDP 用户标签系统 → HVA 研究 · 追问 → glm-5.3 备选 → 候选行为获得支持（仍属候选） → 已停止 → 智能体 → 运行中 → 首页推荐位 / 搜索结果页 → 黄金眼`，与 `Intl.Collator('zh-Hans-CN')` 拼音序**完全不同**；`COLLATE NOCASE` 只折 ASCII 大小写（会改变 `glm` 与 `HVA` 的相对次序），对中文无效。**因此前端下拉顺序不得依赖数据库对中文名的默认排序**；而 `CFG-08 dict_item` 已有 `order_no int NOT NULL`（`schema.md:621`「展示顺序」），**零 schema 改动**即可彻底规避——字典查询一律 `ORDER BY order_no`，展示顺序由数据决定，与排序规则和 ICU 版本无关。附：`LIKE` 对 ASCII 大小写不敏感、对中文按字节子串匹配；`GLOB` 与 `IN` 均**区分大小写/按字节精确**（`GLOB '*cdp*'` 不命中 `CDP …`；`IN ('cdp …')` 不命中；`IN ('运行中 ')` 因尾空格不命中）。**注意：以上为 `--local` 结论；2026-09-21 已补 `--remote` 复测（真实 D1 `collation-probe` 库，REST 通道），6 组行为逐字节一致，本段结论对线上同样成立。**
