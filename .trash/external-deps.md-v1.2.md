| 7 | **缺口结论** | **只有报名信息，无用户参与明细**——「**活动存在」≠「用户参与了」**，故原型 `e6_limits` ③ 明确该活动明细缺失不能推出「用户受影响」。这是**降级来源的典型缺口：能证明「有活动」，不能证明「活动起了作用」** | ✅ `DB.sources[ACT].cannot`、`e6_limits` ③、`schema.md` §7 |

### 2.6 五系统缺口横向对照（研究缺口的完整地图）

| 想让研究结论更强，缺的是… | 卡在哪个系统 | 影响哪项检验（F-20 五查） | 依据 |
| ---- | ---- | ---- | ---- |
| 行为发生的**精确时序**（谁先谁后） | CDP（无用户级明细） | ② 行为与结果的先后关系 | EV-1038 `missing`、`e6_limits` ② |
| 用户**访问缺失的真实原因**（是否转移站外） | CDP + 黄金眼（均无用户级） | ① 人群可比基础 | OPP-012 `unknown` |
| **商品侧反向解释**（囤货型 / 消耗周期） | PIM（无履约与消耗周期） | ④ 是否存在其他解释 | `e6_limits` ③ |
| **权益增量效果**（不是核销率） | MKT（需另行测算） | ④ 是否存在其他解释 | `DB.sources[MKT].cannot` |
| **用户是否真的参与了活动** | ACT（只有报名） | ④ 是否存在其他解释 | `e6_limits` ③ |

1. **TOL-12 是「被明确判定为不存在」的工具**，不是「待接入」。它的不存在正是 `e6_limits` ③ 的成因——**登记它的不存在，与登记工具本身同样重要**（否则 Agent 会以为「查不到是因为没接」，而非「这个系统根本没有」）。

## 6. mock server 需求清单（对应要求 5）

> 用途：在真实接口未接入时，让 F-14/F-15/F-24/F-26 能被真实地测试——**特别是失败路径**（BRD 硬红线：「不能用模型预期的内容代替查询结果」）。
> 七类行为各一条样例响应。**响应体结构为 demo**（MCP 工具契约未定），但**行为语义与落库字段的对应关系是确定的**（落库字段见 `schema.md` EXT-01）。

**统一约定**：请求含 `tool_code` + `query_condition`；响应须能映射到 EXT-01 的 `result_status` / `result_summary` / `returned_rows` / `fail_reason` / `retry_count` / `restricted_flag`。

### 6.1 延迟（慢响应 → 需触发重试与超时语义）

```json
{
  "tool_code": "act.activity.list *",
  "status": "ok",
  "elapsed_ms": 42000,
  "notice": "接口响应慢 *",
  "data": { "activity_count": 37, "by_type": { "满减": 21, "秒杀": 16 }, "covered_sku": 12000 },
  "warnings": ["响应耗时超过阈值 30s *，已重试 2 次后返回 *"]
}
```

| 映射 | 值 |
| ---- | ---- |
| 落库 | `result_status = ok`、`retry_count = 2`、`fail_reason` 空 |
| 依据 | EV-1027 `at`：「接口响应慢，重试 2 次后返回」 |
| 验收 | F-26 须记录重试次数且**成功不算失败**；F-25 失败也留痕的对照面 |

### 6.2 403（权限不足 → 受限返回，非失败）

```json
{
  "tool_code": "cdp.behavior.agg *",
  "status": "restricted",
  "http_hint": 403,
  "reason_code": "NO_PERMISSION",
  "reason_text": "当前任务未被授权查询该人群范围（超出目标业务范围）",
  "data": null
}
```

| 映射 | 值 |
| ---- | ---- |
| 落库 | `restricted_flag = 1`、`result_status = fail`、`fail_reason = "权限未开通"` |
| 依据 | BRD F-23「权限分支互斥：允许/不允许，不允许时保存原因并返回受限原因」；`schema.md` CFG-03 `restrict_reason`、EXT-01 `restricted_flag` |
| 验收 | 「不允许」须**保存原因并返回受限原因**，不可静默为空 |

### 6.3 空结果（查到了，但什么都没返回）

```json
{
  "tool_code": "pim.spec.distribution *",
  "status": "ok",
  "elapsed_ms": 1800,
  "data": { "sample_size": 0, "items": [] },
  "notice": "条件命中 0 条记录 *"
}
```

| 映射 | 值 |
| ---- | ---- |
| 落库 | `result_status = ok`、`returned_rows = 0`、`result_summary` 须**如实记录「返回 0 行」** |
| 区别于失败 | **空结果是「成功但无数据」**，不得写成 `fail`——否则会污染 F-32「任务未完成」与 F-20 第⑤项的判断 |
| 验收 | 研究侧应产出 `missing_note`（缺口），而非「接口失败」 |

### 6.4 多值字段（一个字段返回多个值，需保序与去重规则）

```json
{
  "tool_code": "pim.category.query *",
  "status": "ok",
  "data": {
    "sku_id": "SKU-88001 *",
    "category_path": ["京东超市", "食品饮料", "乳品烘焙", "常温奶"],
    "spec_tags": ["家庭装", "多件装", "促销装"]
  },
  "notice": "category_path 为层级路径，spec_tags 可能多标签并存 *"
}
```

| 映射 | 值 |
| ---- | ---- |
| 落库 | `query_condition` 须完整记录多值条件；`evidence.applicability_scope` 须说明多值的处理口径 |
| 风险 | **多值字段是「同一概念两种口径」的高发区**（如「家庭装 / 多件装」算一个规格族还是两个）——须在 `evidence` 层说明取值口径，否则 F-20 第①项人群分组会不一致 |
| 依据 | EV-1035 `condition`：「包装规格标签 ∈ {家庭装, 多件装}」 |

### 6.5 不可算字段（字段存在但值不可计算）

```json
{
  "tool_code": "cdp.tag.distribution *",
  "status": "ok",
  "data": {
    "repurchase_rate_30d": null,
    "repurchase_rate_30d_reason": "样本量不足（n=37），不满足最小样本阈值 *",
    "sample_size": 37
  },
  "notice": "部分指标未计算 *"
}
```

| 映射 | 值 |
| ---- | ---- |
| 落库 | `result_summary` 须**原样保留「不可算」及原因**，不得省略该字段 |
| 关键区别 | **「不可算」≠「等于 0」≠「失败」**。三者混淆会让 F-20 第⑤项「信息是否足以支持判断」得出错误结论 |
| 验收 | 若以此作为证据，`missing_note` 须写明「该项不可算，不影响/影响哪项判断」 |

### 6.6 中英枚举不一致（外部枚举与本地字典不对齐）

```json
{
  "tool_code": "hje.traffic.entry *",
  "status": "ok",
  "data": {
    "entry_type": "SEARCH_RESULT_PAGE",
    "entry_type_raw": "搜索结果页",
    "conversion_status": "SUCCESS"
  },
  "notice": "本系统枚举为英文，原始值为中文，需归一化 *"
}
```

| 映射 | 值 |
| ---- | ---- |
| 落库 | `evidence.result_summary` 原样保留；**归一化规则须登记**（否则同一入口在不同证据里写法不同，`applicability_scope` 无法对齐） |
| 依据 | `schema.md` §8「同一概念只允许一个命名」与 CFG-07/08 字典表；外部枚举**不得直接落库**，须落字典项 |
| 验收 | `dict_item.item_code`（英文编码）与 `item_name`（中文口径）分离——本类响应正是该设计要解决的问题 |

### 6.7 覆盖边界（查询区间刚好跨在数据边界上）

```json
{
  "tool_code": "hje.traffic.entry *",
  "status": "ok",
  "data": {
    "rows": [ { "period": "2026-07-01 ~ 2026-09-15", "value": 18.4 } ],
    "coverage": { "requested": "2026-07-01 ~ 2026-09-15", "actual": "2026-07-01 ~ 2026-09-10", "truncated_days": 5 }
  },
  "notice": "实际数据仅覆盖至 2026-09-10，尾部 5 天缺失 *"
}
```

| 映射 | 值 |
| ---- | ---- |
| 落库 | `evidence.info_time_point` 须**写实际覆盖区间而非请求区间**；`returned_rows` 与请求区间不一致时须显式说明 |
| 关键区别 | 覆盖边界不完整是**常见的静默陷阱**：结果看起来成功，但缺失尾部天数会让「目标关注时段延长至 9/15」（原型目标 v3 的变更）落空 |
| 依据 | 原型目标 v3 变更：「关注时段延长至 9/15」；`schema.md` EXT-02 `info_time_point` 口径为「取数时刻 + 覆盖的业务时段」 |
