## 1. Q-03 · 业务背景要不要跟目标版本一起定版

### 1.1【事项】

Q-03：**"业务背景"这一层信息，要不要和目标版本绑在一起做快照？**

换句话说——当一份研究回头看时，平台能不能说清"**这次研究用的是哪一版背景**"？还是说只要说清"当时的目标和范围"就够了，背景不必定版。

用业务语言讲：目标会更新（v1→v2→v3），更新时旧版本原样留着，所以过去的研究能说清"我当时是按 v2 的目标做的"。**问题是背景（业务知识、业务约束、口径说明）算不算同样要留档的那一层**——它现在是"知识库"形态（随时可增补、可停用），不是"定版"形态。

### 1.2【为什么现在必须定】

**要改的是什么**：`MD-04 business_context`（业务背景表，`schema.md` L213–L227）以及与它相邻的两张表——`MD-02 research_goal_version`（L174–L195）、`MD-07 research`（L263–L287）。若选"联动"，`MD-04` 需增一个版本引用列（或另建快照表）；若选"不联动"，表结构不动，但需在 `CFG-06` / `PD-06` 的口径里补一句责任归属。

**建表后改的代价，具体到落点**：

| 层面               | 具体代价 |
| ---------------- | ---- |
| **表**            | 主改 `MD-04`；连带核对 `MD-02`（版本主表）、`MD-07`（研究的启动快照）、`PD-06 context_injection`（注入记录） |
| **字段**           | 联动需在 `MD-04` 增列（如 `goal_version_no`）或另建 `business_context_version`；`MD-04` 现有字段 `context_id / goal_id(可空) / context_kind / title / content / source_ref / is_active / created_at` 均无版本语义 |
| **migration 文件** | `db/migrations/` **尚未创建**（当前 `db/` 下只有 `probes/`，见 `db/README.md`）。DDL 一旦落盘再加列，需**新 migration + 回填存量行**；而存量背景行**无法回填版本**（当时没记录），只能置空 → 形成"**半联动**"（新数据有版本、老数据没有），这本身是个坑 |
| **引用卡**          | `schema.md` §8.1（命名唯一性表，若新增"背景版本"概念需加行）；§10 覆盖矩阵 **F-07 / F-12** 两行；§11 索引建议（若加版本列，可能需配索引）；本文件 §4 连带影响 |
| **原型页面/字段**      | **无原型可对照**。全库检索确认：原型 `assets/data.js` 的 `goal` 对象只有 `fields`（六要素）+ `materials` + `versions`，**没有任何"背景"数据结构**；`prototype/pages/*.html` 中"背景 / context"**零命中**。所以 Q-03 是**原型未覆盖的新增领域**——裁决后不存在"原型跟着改"的动作，但也**没有已钉死的需求可作为判据** |

**顺带核对你的问题**：不联动的话，"目标更新后已有研究保留启动时目标和范围"由谁保证？

**答：由 `MD-02` + `MD-07` 保证，与 `business_context` 无关——所以"不联动"并不会破坏这条口径。** 证据链：

- `MD-02` 注释（`schema.md` L176）明写：「一次保存形成一行完整快照。**目标更新不改旧行**，新版本新增一行——**这是 F-01「已有研究保留启动时采用的目标和范围」的存储基础**。」
- `MD-07` 的两个字段（L280–L281）是**启动时快照**：`goal_id`（「启动时快照的目标（**不随目标更新而变**）」）、`goal_version_no`（「启动时快照的目标版本号；**后续目标更新不影响本研究**」）。
- 而"**目标和范围**"具体落在 `MD-02` 的 `business_goal`（①）、`business_scope`（③）、`focus_period`（④）。**业务背景（`MD-04`）不在六要素之内**——它由 F-07 独立管理（「目标与口径之外的业务知识与约束」，见 `MD-04` 注释 L215）。

**真正的缺口**（这才是 Q-03 要害）：**背景本身没有版本**。`MD-04` 只有 `created_at`（登记时点）+ `is_active`（是否生效）。因此"研究启动当时用的是哪一版背景"**无法精确回答**；近似手段是 `PD-06 context_injection`——它记录"某任务实际注入了哪些对象"（`ref_object_type` + `ref_object_id`，L490–L491），`CONTEXT_TYPE` 字典里确有 `background = 背景`（L832）。但 `PD-06` **只指回那一行**：若该背景行内容被**就地修改**，取回的是"现在的内容"，不是"当时的内容"。

**另有一处结构性问题必须先知会**：`MD-04.goal_id` **可为空**（L221：「平台级通用背景为空」）。若给背景挂"目标版本号"，**平台级背景将无版本可挂**——这是"联动"方案绕不开的约束。

### 1.3【选项】

#### 选项 A：联动——背景随目标版本定版

- **方案一句话**：`MD-04` 增 `goal_version_no`，每条背景归属到某个目标版本；查研究时按 `research.goal_version_no` 连带取回当时那版背景。
- **影响的表与字段**：主改 `MD-04`（新增 `goal_version_no`，逻辑关联 `MD-02`）；连带 `MD-02`（版本语义被扩展）、`PD-06`（注入记录可简化）；`MD-04.goal_id` 为空的行（平台级背景）**无法挂版本**，需额外规则。
- **对功能点有利/不利**：
  - 有利 **F-12**（「一阶段给：目标、**背景**…」——注入的确定性更强，注的是"定版"背景）
  - 有利 **F-01** 的衍生要求（把"不混两个时期的判断"扩展到背景层）
  - 不利 **F-07**（业务背景管理）：F-07 的形态是"背景库可增补"，一增补就要 bump 目标版本，会把**目标版本**污染成**知识版本**——目标版本本应在六要素变化时才 bump
- **实现成本**：中（改表 + 定版规则 + 平台级背景的例外规则 + 存量回填无解）
- **将来反悔的难度**：中—高。改回去要删列/停用快照表，且**已按此写入的数据会形成"背景版本 ≠ 目标版本"的历史口径**，清理需人工判断

#### 选项 B：不联动（维持现状）

- **方案一句话**：`MD-04` 结构不动；"目标和范围"由 `MD-02` + `MD-07` 保证，背景靠 `created_at` + `is_active` 表达时间线。
- **影响的表与字段**：**无字段变化**；仅在 `CFG-06` / `PD-06` 的口径文字里明确"背景注入以 `PD-06` 记录为准"。
- **对功能点有利/不利**：
  - 有利 **F-01**（口径链条干净：版本只由六要素驱动，语义不被污染）、**F-07**（背景保持"知识库"的增补形态）
  - 不利 **F-12 / F-31**：**无法精确回溯"研究启动时的背景"**——只能回溯"注入了哪几条"（`PD-06`），回溯不到"那几条当时的内容"
- **实现成本**：**最低**（零结构变更）
- **将来反悔的难度**：**低**。将来若发现确需回溯背景，再加快照机制即可，且反悔时无需清理（现状无历史包袱）——**唯一不可逆的损失是"过去这段时间的背景变更没有留痕"**

#### 选项 C：背景独立版本化（不挂目标版本）

- **方案一句话**：`MD-04` 增自己的版本号 + 生效标记（类比 `MD-02` 的 `version_no` + `is_applied`），**不回挂 `goal_version_no`**；研究侧若要快照背景，另加一列（如 `research.context_version_snapshot`）或明确由 `PD-06` 承担。
- **影响的表与字段**：`MD-04`（新增版本列、生效标记）；可能连带 `MD-07`（新增背景版本快照列）或 `PD-06`（明确记录背景版本）；平台级背景（`goal_id` 为空）**仍可版本化**（这正是与选项 A 的关键差异）。
- **对功能点有利/不利**：
  - 有利 **F-07**（背景自主演进，不绑死目标版本）、**F-12**（可精确回溯背景版本）
  - 不利：`MD-04` 从"轻表"变"重表"，**F-07 的登记动作变重**（每次增补要定版），与 F-07「以任务形式提示待补」「背景库」的轻量定位有张力
- **实现成本**：中—高（等于给 `MD-04` 引入一整套版本机制，与 `MD-02` 平行）
- **将来反悔的难度**：低—中（机制独立，撤回不影响 `MD-02`）

### 1.4【推荐】

**倾向：选项 B（不联动），但把责任显式写进 `PD-06` 的口径。** 置信度：**中**。

理由：

1. **F-01 那条口径本来就不靠 `business_context` 保证**（§1.2 已给出证据链），所以"不联动"不是"放弃要求"，而是"**该要求已由另外两张表满足**"。
2. `MD-04` 的设计形态是**增补式知识库**（`is_active` 开关 + `created_at`），`MD-02` 是**定版式快照**。强行让前者遵循后者的语义，会制造"背景一增补就要 bump 目标版本"的耦合——**这恰恰是"不混两个时期的判断"想避免的**。
3. 选项 A 有一处结构性硬伤：`MD-04.goal_id` 可为空（平台级背景），**这类行没有版本可挂**，方案必然要开例外口子。
4. 选项 C 方向正确但成本偏高，且与 F-07 的轻量定位有张力——**在当前阶段（尚无 migration、无真实数据）它的收益还兑现不了**。

**置信度非高，缺的信息是**：

- **F-07 背景的实际变更频率与变更方式**（是"新增条目"为主，还是"就地改内容"为主）。若以就地改为主，则"背景必须定版"的诉求成立，应改推选项 C。**这条只有你或业务方能回答**。
- **BRD 是否有"背景变更需影响在研研究"的要求**——我在 BRD 里**没有找到**对应条文（F-01 的 `impact_note` 只管目标版本变更影响）。若业务上确实要求"背景变更也要提示影响范围"，则 B 明显不够。**这条需要你确认 BRD 是否漏了一条功能点。**

### 1.5【反向验证】

- **若选选项 A（联动）**：**无功能点因此无法实现**。但会产生一个**口径副作用**：F-27 目标配置页的「版本变化可见」会把"背景增补"也算成一次"目标版本变化"，**UI 上的版本语义会与业务理解的"目标版本"不一致**——这不是"无法实现"，是"实现后会歧义"。另需说明：`MD-04` 平台级背景（`goal_id` 为空）的行**无法融入联动模型**，属方案内的表达力缺口。

## 3. Q-05 · 机会六要素要不要强制必填（重点：未知项）

### 3.1【事项】

Q-05：**机会的六个要素（对应目标 / 涉及对象 / 观察现象 / 初步依据 / 研究理由 / 未知项）要不要在库里强制"必须填"？** 尤其**「未知项」**这一项——**能不能留空**？

业务语言讲：一个机会被记录下来时，六项都得写清楚；但"未知项"这一项的意思是"我还查不清的东西"，那**当真的什么都查清了、没有未知项时，这一栏该写什么**？

### 3.2【为什么现在必须定】

**现状（必须先说清，因为 §12 的措辞与表定义不自洽）**：

- `MD-06 opportunity`（`schema.md` L242–L261）里，六要素对应字段是：**「对应目标」走 `goal_id`(L250) + `goal_version_no`(L251)**，其余五项是 `target_object`(L254)、`phenomenon`(L255)、`initial_basis_note`(L256)、`research_reason`(L257)、`unknown_item`(L258)——**这六项（含 `goal_id`/`goal_version_no`）的"是否可空"列全部标 `N`**（NOT NULL）。
- **但**：`schema.md` §12 里 Q-05 的原话是「是否需要对 `opportunity` 的六要素做「必填」强制（**当前 `unknown_item` 可为空说明**）」——这句话**与表里 `unknown_item` 标 `N` 不一致**。两种读法：① "可为空说明" = "可以为空说明"（即允许留空）→ 与 `N` 冲突；② "可为空（的）说明" = 描述其语义是"可留空的说明"→ 也隐含允许留空。**无论哪种读法，都与 `N` 打架。** 已列入 §5「核对中发现的上游缺陷」，**未擅自改**（本预填在 §3.7 给出了处置方向，供落章时一并确认）。
- **更关键的技术事实（来自 D1 实测）**：`db/probes/type/README.md` 的实测结论——**`NOT NULL` 并不拦空串**（D1 里 `varchar(n)` / `text` 写入 `''` 与 `NULL` 是**可区分**的两种状态）。**所以：当前标 `N` 的六要素，实际上一条都没被真正"强制非空"**——写空串照样入库。"必填"若要落地，**必须加 `CHECK`**，光靠 `NOT NULL` 没用。

**建表后改的代价，具体到落点**：

| 层面               | 具体代价 |
| ---------------- | ---- |
| **表**            | `MD-06 opportunity`（六要素字段 + 若要"必填"则加 CHECK） |
| **字段**           | 六个要素字段（「对应目标」= `goal_id` + `goal_version_no`；其余五项 = `target_object` / `phenomenon` / `initial_basis_note` / `research_reason` / `unknown_item`）+ `opportunity_title` |
| **migration 文件** | `db/migrations/` **尚未创建**；改约束 = 新 migration + **存量行校验**（一旦有存量空值，加 CHECK 会**直接失败**，须先清洗）——"加 CHECK 比去 CHECK 难得多" |
| **引用卡**          | `schema.md` §8.1（若命名调整）、**§10 覆盖矩阵 F-10 / F-28 两行**、§11 索引（`opportunity` 的 `(goal_id, opportunity_status)`，L886，与必填无直接关系但要回归）；本文件 §4 |
| **原型页面/字段**      | `prototype/pages/opportunities.html` **L293** 渲染 `o.unknown`（「未知项」字段）；`prototype/pages/propose.html` **L93** 同样渲染 `o.unknown`。数据源 `assets/data.js` 的 `opportunities[].unknown` |
| **原型实测事实**       | 原型共 **8 条机会**（OPP-014 / 013 / 012 / 011 / 010 / 009 / 006 / 005），**8 条的 `unknown` 全部有实义内容，无一条为空或空串**（如 OPP-011：「未核销原因（门槛 / 品类不适用 / 遗忘）无数据支撑」）。**即：mock 数据里从未出现"没有未知项"的机会**——所以"该不该允许空"这件事，**原型没有提供反例**，这也正是它成为待决项的原因 |

### 3.3【选项】

#### 选项 A：六要素全部强制非空（含 `unknown_item`）

- **方案一句话**：六字段全部 `NOT NULL` + `CHECK (length(trim(x)) > 0)`，空串也拒。
- **影响的表与字段**：`MD-06` 全部六要素字段
- **对功能点有利/不利**：
  - 有利 **F-28**（验收要点「**六要素齐全**」，L292 字面达成）
  - **不利 F-15**：F-15 验收要点是「对现象的解释**必须标明尚未验证的部分**」（L195）。当一条机会**确实没有未知项**时，选项 A 会**逼出编造的未知项**——把"已查清"硬写成一条假的"待验证"。这与"**允许保留待查证解释**"的**本意相反**（本意是"允许不完整"，不是"强迫假装不完整"）。
- **实现成本**：低（六条 CHECK）
- **将来反悔的难度**：**中**。放宽容易，但**一旦按此规则写入了"填充式未知项"，这些假数据已入库**，事后无法自动区分"真未知"与"为过约束编的未知"——**这是不可逆的数据污染**

#### 选项 B：`unknown_item` 允许为空，其余五要素强制非空

- **方案一句话**：五个实体字段加 `CHECK` 非空；`unknown_item` 保持 `N` 但**允许空串**（或直接改 `Y`）。
- **影响的表与字段**：`MD-06` 的五字段 + `unknown_item`
- **对功能点有利/不利**：
  - 有利 **F-15**（"允许不全"落地）
  - 不利 **F-28**：若「六要素齐全」被解释为"六项都有值"，则 `unknown_item` 为空的机会可能被判不合格
- **实现成本**：低（五条 CHECK）
- **将来反悔的难度**：低

#### 选项 C：用 `NULL` / 空串区分"未评估"与"已评估且确无未知项"

- **方案一句话**：`unknown_item` 允许 `NULL`（= **未评估**，视为六要素不齐、触发待补）+ 允许 `''` 或固定值（= **已评估、确无未知项**）；其余五要素 `CHECK` 非空；判定"齐不齐"时 `unknown_item IS NULL` 即不齐。
- **影响的表与字段**：`MD-06.unknown_item`（语义分层）+ 五要素的 CHECK
- **对功能点有利/不利**：
  - **同时有利于 F-15 与 F-28**：「六要素要说清楚」由"**六项都有评估状态**"满足；「允许保留待查证解释」由"**未知项可为'无'**"满足
  - 风险：需要**应用层明确约定谁写 `NULL`、谁写 `''`**（D1 实测二者**可区分**，这是本方案的技术前提——已由 `db/probes/type/` 证实）
- **实现成本**：**中**（结构最轻，但多一个"两个空状态语义"的约定，前端与写入侧都要遵守；混用会让语义失效）
- **将来反悔的难度**：**低—中**（结构不变，退化为选项 B 只需改约定）

### 3.4【课程口径对照】（你要求核对的冲突）

**先说来源的诚实声明**：你提到的两句「**允许保留待查证解释**」与「**六要素要说清楚**」——**本库内查无原文**。全库检索 `待查证` / `说清楚` 均无这两句。它们是**你转述的课程口径**。**最接近的库内落点是**：

| 课程口径（你转述） | 最接近的库内落点 | 原文 |
| --------- | ---- | ---- |
| 允许保留待查证解释 | BRD **F-15 基础查证** 验收要点（`BRD.md` **L195**） | 「对现象的解释**必须标明尚未验证的部分**；支持"值得进一步研究"，不给完整人群对照和 HVA 结论」 |
| 六要素要说清楚   | BRD **F-28 机会列表与详情页** 验收要点（`BRD.md` **L292**） | 「**六要素齐全**；证据可回查到查询记录」 |

**是否冲突——表面冲突，实质不冲突，冲突只在一种实现下发生**：

- 两条约束的**对象不同**：**F-15 约束"解释的完整性"**（允许不全，但**必须标明哪里不全**）；**F-28 约束"六要素的记录完整性"**（六项都要有落点）。二者作用在**不同层**，本身可共存。
- **冲突只发生在一种实现下**：把"未知项"强制成"**必须有实义未知**"——那就把 F-15 的"允许不全"改写成了"**必须编造不全**"。

**两种约束写法各自满足哪一条**：

| 约束写法 | 满足「六要素要说清楚」(F-28) | 满足「允许保留待查证解释」(F-15) |
| ---- | ---- | ---- |
| **写法一**：六字段全部 `CHECK` 非空 | ✅ **字面满足** | ❌ **不满足**（确无未知时只能编造） |
| **写法二**：五字段非空 + `unknown_item` 允许为空 | ⚠️ **取决于"齐全"的解释**（"六项都有值"→不满足；"六项都被评估过"→满足） | ✅ **满足** |
| **写法三**（选项 C）：五字段非空 + `unknown_item` 用 `NULL`/空串区分"未评估"与"确无" | ✅ **满足**（六项都有评估状态，无"漏评估"） | ✅ **满足**（"确无未知项"是合法取值，不必编造） |

> 综上：**若你希望两条课程口径同时成立，写法三是唯一同时满足的写法**；写法一与写法二各牺牲一条。

### 3.5【推荐】

**倾向：选项 C（`NULL` / 空串二态），其次选项 B。** 置信度：**中**。

理由：

1. 它是**唯一能同时满足你转述的两条课程口径**的写法（§3.4 表）。
