# ADR-001 · 业务背景不与目标版本联动

## 1. 问题

**业务背景（`MD-04 business_context`）要不要与目标版本（`MD-02 research_goal_version`）一起定版？**

业务侧的问法：一份研究回头看时，平台能不能说清「**这次研究用的是哪一版背景**」？还是说清「当时的目标和范围」就够了，背景不必定版。

**张力来自两张表的设计形态不同**：

| 表 | 形态 | 结果 |
| ---- | ---- | ---- |
| `MD-02 research_goal_version` | **定版式快照**——一次保存形成一行完整快照，目标更新不改旧行 | 「这项研究是按 v2 的目标做的」**可回答** |
| `MD-04 business_context` | **增补式知识库**——只有 `created_at`（登记时点）+ `is_active`（是否生效） | 「当时那版背景长什么样」**不可回答** |

**另一条必须先说清的事实**：业务上「目标更新后已有研究保留启动时目标和范围」这条要求，**本来就不由 `business_context` 保证**。证据链：

- `MD-02` 注释（`schema.md`）明写「目标更新不改旧行……这是 F-01『已有研究保留启动时采用的目标和范围』的存储基础」；
- `MD-07` 的 `goal_id` / `goal_version_no` 是**启动时快照**（「不随目标更新而变」）；
- 而「目标和范围」落在 `MD-02` 的 `business_goal`（①）/ `business_scope`（③）/ `focus_period`（④）——**业务背景不在六要素之内**，它由 F-07 独立管理。

**因此本决策不是「要不要放弃某条要求」，而是「要不要为一条 BRD 里没有明写的能力额外付结构成本」。**

## 2. 备选

| 选项 | 一句话 | 影响的表与字段 | 实现成本 | 硬伤 |
| ---- | ---- | ---- | ---- | ---- |
| **A · 联动** | `MD-04` 增 `goal_version_no`，背景随目标版本定版 | `MD-04` 增列；连带 `MD-02`（版本语义被扩展）、`PD-06` | 中 | ① **`MD-04.goal_id` 可为空**（平台级背景）→ 这类行**无版本可挂**，方案必然开例外口子；② 背景一增补就要 bump **目标**版本，把「目标版本」污染成「知识版本」 |
| **B · 不联动** | 结构不动，背景靠 `created_at` + `is_active` 表达时间线 | **无字段变化**；仅在 `CFG-06` / `PD-06` 补口径文字 | **最低**（零结构变更） | 无结构硬伤；代价落在**可回溯性**——答不出「当时那版背景的内容」 |
| **C · 背景独立版本化** | `MD-04` 增自己的版本号 + 生效标记，**不挂**目标版本 | `MD-04` 增版本列、生效标记；可能连带 `MD-07` 或 `PD-06` | 中—高 | 平台级背景**可**版本化（优于 A），但等于给 `MD-04` 引入一整套与 `MD-02` 平行的版本机制，与 F-07「背景库」的**轻量定位**有张力 |

**功能点利弊（要点）**：

- 选项 A：有利 F-12（注入确定性更强）；**不利 F-07**（背景增补会污染目标版本语义）。
- 选项 B：有利 F-01（版本只由六要素驱动，语义干净）、F-07（保持增补形态）；**不利 F-12 / F-31 的可回溯精度**。
- 选项 C：有利 F-07 / F-12；不利点是 `MD-04` 从轻表变重表、F-07 的登记动作变重。

## 3. 最终

**采纳选项 B —— 不联动，并把责任归属显式落成明文。**

落地三件事（均已在 `schema.md` v1.2 完成）：

| # | 动作 | 落点 |
| - | ---- | ---- |
| 1 | **`MD-04` 零结构变更** | 不加版本列、不加快照表 |
| 2 | 明确**注入什么** | `CFG-06` 口径：`background` 类型注入的是 `MD-04` 的**当前生效条目**（`is_active = 1`） |
| 3 | 明确**责任边界** | `PD-06` 口径：「研究启动时采用的是哪一版背景」**以 `PD-06 context_injection` 的记录为准**（记下注入了哪几条对象），**不承担「当时的内容是什么」的还原责任** |

> **为什么第 2、3 条必须写进文档**：否则「不联动」会变成一条**无主口径**——将来有人问「背景版本谁负责」，既不在 `MD-04` 也不在 `PD-06`，无人可答。把代价写成明文，是选择 B 的必要组成部分，不是附赠。

## 4. 权衡

| 得到 | 失去 |
| ---- | ---- |
| **零结构变更**——在建表前定，不产生 migration 返工 | **内容级可回溯性**——「研究启动时那版背景写的是什么」**答不出**，只能答「注入了哪几条」 |
| **语义不被污染**——目标版本只由六要素驱动，F-07 保持「知识库」的增补形态 | BRD **没有**一条验收要点要求回溯背景内容（已逐条查 F-01 / F-07 / F-12 / F-27）——**失去的是一项从未被要求的能力** |
| 避开 A 的结构硬伤：平台级背景（`goal_id` 为空）无版本可挂 | 若 F-07 的背景**以「就地改内容」为主**（而非新增条目），则「当时内容」的丢失会真实发生——见 §6 作废条件 |
| **反悔成本最低**——将来若确需回溯，另加快照机制即可，且无需清理历史（现状无历史包袱） | — |

**结论**：在「无 migration、无真实数据」的当前阶段，选项 C 的收益**尚无法兑现**，而成本立刻发生；选项 A 有结构性硬伤。**B 是当下唯一「零成本 + 无硬伤」的选择**，且其唯一代价（历史内容不留痕）在 BRD 中无对应要求。

## 6. 回滚代价

| 想要改成 | 需要做什么 | 代价 |
| ---- | ---- | ---- |
| B → **C**（背景独立版本化） | `MD-04` 增版本列 + 生效标记；`MD-07` 或 `PD-06` 增背景版本快照列 | **低—中**：结构可加，无需清理历史（因为 B 期间没有写任何版本数据） |
| B → **A**（联动） | 同 C 再加 `goal_version_no`，并处理平台级背景的例外规则 | **中—高**：需为「`goal_id` 为空」的行定例外；且已写入的数据会形成「背景版本 ≠ 目标版本」的历史口径 |
| **不可逆的部分** | —— | **B 期间发生的背景变更没有内容留痕**。将来补机制**无法回溯这段时间**，只能从机制上线时点开始记录。这是本决策**唯一不可逆的损失**，已知并接受 |

## 7. 前置核对条件（作废条件）

本决策在 `DEC-PACK-001` §1.4 标注了置信度 **中**，并附两条信息缺口。**下列任一成立时，本 ADR 应作废并重开**：

1. **F-07 背景以「就地改内容」为主**（而非新增条目为主）→ 「背景必须定版」的诉求成立，应改推**选项 C**；
2. **BRD 漏了一条「背景变更需影响在研研究」的功能点** → 选项 B 不足，须在 **C / A** 中重选。

> 两条均只有 PM 或业务方能回答。在核对结论出来前，本 ADR 按 B 执行，但**不宣称这是终局最优解**。
