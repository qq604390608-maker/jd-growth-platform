## 1. 模块目标与定位

M2 是平台的**信息存储中枢**：保存并组织与研究有关的信息——两阶段共同使用的背景，以及研究过程中逐步增加的机会、问题和证据。核心定位是「**共享上下文本体是数据库不是文件夹**」：存的是内容或来源引用，按任务挑选相关部分注入。它让机会发现（M3）与 HVA 分析（M4）两个阶段共享上下文、避免重复研究。

## 2. 范围

**In scope**：F-07~F-12（业务背景、可用来源与工具登记、证据管理、机会记录、研究结果与历史、上下文按任务组织注入）。
**Out of scope**：Agent 的研究判断（M3/M4）、查询执行（M5）、前端展示（M6）。研究结论的"外部验证执行与效果计算"由业务工作完成，本模块只负责登记与关联（F-11）。

## 3. 功能需求

### F-07 业务背景管理

- **功能描述**（继承 BRD §4）：维护目标与口径、业务知识与约束；触点清单（首页推荐位、搜索结果页、京东超市频道等）。
- **输入 → 输出**：业务方材料＋预置触点 → 背景库。
- **验收要点**：Agent 查询前可获知"能查哪些、该往哪个方向查"。
- **关联 schema**：`MD-04 business_context`（背景主体）、`MD-05 touchpoint`（触点清单）。
- **依赖与衔接**：下游被 M3/M4 作为背景上下文消费；触点被 M5 TOL-05 坑位曝光等查询引用。

### F-08 可用来源与工具登记

- **功能描述**（继承 BRD §4）：登记五类外部系统与工具用途。**系统名称确定了信息归属，实际可查内容需通过接入能力确认**：线上流量信息 ≠ 完整用户行为序列，活动信息 ≠ 活动效果；未接入或无法查询的信息成为研究缺口，不能用系统名称代替实际证据。
- **输入 → 输出**：接入能力 → 来源与工具说明。
- **验收要点**：Agent 能知道缺少什么信息，但实际查询仍需对应接入（缺口须如实登记）。
- **关联 schema**：`CFG-01 source_registry`（五类来源：CDP/HJE/PIM/MKT/ACT，含 `can`/`cannot`/`status`）。
- **关联外部依赖**：来源与缺口语义见 `external-deps.md` §2（五系统 `can`/`cannot`/`status`，含 P0 阻断/P1 削弱/P2 降级分级）。
- **依赖与衔接**：下游＝M5（工具注册与权限）、M3/M4（缺口感知）。

### F-09 证据管理

- **功能描述**（继承 BRD §4）：每项证据关联来源、查询条件、信息时点、适用范围和缺失说明——无论哪个 Agent 引用，都应能回查证据是怎样取得的。**新证据加入不覆盖原有依据**：初查后业务条件变化可重新查询，原观察仍保留当时依据。
- **输入 → 输出**：查询返回 → 结构化证据记录。
- **验收要点**：证据链完整可回溯；新旧依据并存且关联。
- **关联 schema**：`EXT-02 evidence`（证据主体，含 source_id/query_condition/info_time/scope/missing_note）、`LNK-01 opportunity_evidence`（机会↔证据）、`LNK-02 finding_evidence`（关键发现↔证据）。
- **依赖与衔接**：证据由 M5 `EXT-01 query_record` 转化而来；供 M3/M4 回查、M6 F-28/F-30 展示。

### F-10 机会记录管理

- **功能描述**（继承 BRD §4）：机会六要素：对应目标 / 涉及对象（人群、品类或旅程环节）/ 观察现象 / 初步依据（资料或查询的来源与时点）/ 研究理由 / 未知项。同一问题出现新证据 → 关联到已有机会；新现象有独立价值 → 新机会记录；**暂不研究的机会仍保留记录**，条件变化或新证据后可再选。
- **输入 → 输出**：机会发现产出 → 机会记录（含状态）。
- **验收要点**：机会选择取决于证据、相关性与问题是否值得追问，而非文案是否肯定。
- **关联 schema**：`MD-06 opportunity`（机会主体，六要素＋`unknown_item` 二态）、`LNK-03 opportunity_relation`（机会↔机会，去重/关联）、`PD-05 opportunity_status_log`（状态变更：候选/暂不研究/已提交研究）。
- **关联决策**：机会六要素必填与未知项二态见 `ADR-003`（对应 `schema.md` Q-05 裁决）。
- **依赖与衔接**：上游＝M3 产出；下游＝M1 F-03 人工节点选机会。

### F-11 研究结果与历史管理

- **功能描述**（继承 BRD §4）：保存研究结果、历史研究；后续业务工作形成验证结果时，平台可关联其结论与来源供以后研究查阅（外部验证的执行与效果计算由业务工作完成）。
- **输入 → 输出**：研究结果＋外部验证 → 历史研究库。
- **验收要点**：后续研究可引用历史，避免重复研究。
- **关联 schema**：`MD-07 research`（研究主体）、`MD-08 research_finding`（关键发现）、`EXT-03 external_validation`（外部验证结果）。
- **依赖与衔接**：上游＝M4 产出；下游＝M3/M4 作为历史上下文注入。

### F-12 上下文按任务组织注入

- **功能描述**（继承 BRD §4）：两个维度——**类型**（需要什么类型的信息）＋**范围**（只查和京东超市有关的触点 / 只看业务方负责的品类），以类型为主、范围是具体约束。一阶段给：目标、背景、可用来源、已有机会摘要；二阶段增加：所选机会、产品问题、已有证据、相关历史研究。
- **输入 → 输出**：任务描述 → 该任务的工作空间初始化。
- **验收要点**：初始化是确定性程序行为，不是每回随机；只传递一句"继续分析"无效，要求 PM 重新粘贴全部资料也不应发生。
- **关联 schema**：`PD-06 context_injection`（注入记录）、`CFG-06 context_template`（注入模板，按任务类型×上下文类型组合）。
- **依赖与衔接**：被 M1 F-02/F-04 调用；供 M3/M4 启动时使用。

## 4. 关键约束与红线

1. **本体是数据库**：共享上下文是结构化存储（D1），不是文件目录；按任务挑选相关部分注入。
2. **证据可回溯**：证据必须带来源、条件、时点、适用范围（BRD §7 第 3 条）；新旧依据并存不覆盖。
3. **缺口如实**：来源未接入/能力不足须登记，不得用系统名称代替实际证据（BRD 术语口径、F-08）。
4. **白盒原则**：F-07~F-12 逐点验收、双向引用。

## 5. 验收总则（模块级，承接 BRD §7）

- 证据链完整可回溯；机会六要素齐全且未知项二态正确。
- 上下文注入确定性可复现（同任务同输入→同工作空间）。
- 历史研究可被后续研究引用，避免重复研究。
